Project Rules & Rules of Engagement
Every real security engagement operates under a signed Rules of Engagement (ROE) document. Yours is below. These rules are not optional — work outside this scope is not part of the assessed engagement and may violate your institution's acceptable use policy.
Scope
This engagement is authorized only against the lab environment you personally build for this project: your own virtual machine(s), reachable from WSL (or a fallback attacker VM, see Lab Setup Guide). Never scan, probe, or attack a device you do not personally own or control — including other devices on a shared dorm, office, or public Wi-Fi network.
Rules
Only assess systems inside your own lab. Never scan, probe, or attack a public website, IP address, or a device you don't personally own.
Never attack, scan, or access another student's machine or account, even if invited to.
Password attacks are limited to accounts you created yourself inside the lab.
Every action you take that produces a finding must be backed by evidence (screenshot, terminal output, or log excerpt) — undocumented claims will not be credited.
If WSL cannot reach your target VM even after switching to a bridged network adapter, add a second lightweight Linux VM as your attacker environment instead — do not work around this by bridging onto a network you don't control.
If you are ever unsure whether something is in scope, stop and ask your instructor before proceeding.
The vulnerable target must stay inside your approved lab. Because Metasploitable2 is intentionally insecure, never expose it to the public Internet or leave it reachable from devices you do not control.
Only the assigned target IP may be assessed. Never scan your whole home, school, office, or public network — scan the single target address, not a broad range.

Doing R&D — How to Research Like a Consultant
This handbook deliberately tells you what to achieve, not the exact commands to type. That is not an oversight — it is the single most important skill this program builds. In a real engagement, no one hands a consultant a script. You are given a goal, and you research your way to it. The tasks ahead assume you will look things up, try things, hit errors, and work through them. The tips below are how to do that well, so that "figure it out yourself" feels like a method rather than a wall.
Go to the official source first. For every tool in this lab — VirtualBox, Metasploitable2, DVWA, Wazuh, Nmap, Hydra — the project's own documentation is the most reliable answer, and it is written for the exact version you are running. Read the official docs before a random blog post, because installer commands and file paths change between versions and outdated tutorials are the most common reason a step "doesn't work."
Read the error message before you search. The error almost always names the problem — a missing package, a permission denied, a connection refused, a wrong path. Read it in full, then search for the exact text of the error (in quotes) rather than a vague description like "it won't work." The precise message is what leads you to the precise fix.
Use the tool's own help. Before searching the web, try the built-in manual: the man command, or a tool's --help flag, lists every option straight from the source. Learning to read a man page is faster than hunting for the right blog and is a core habit of everyone who works in this field.
Change one thing at a time. When something breaks, resist changing five settings at once. Change one, test, and observe. This is how you learn what each setting actually does — and if you fix it, you will know exactly why, which is the difference between guessing and understanding.
Understand before you paste. You will find commands online. Before you run one — especially anything with sudo — make sure you can explain in one sentence what it does. Never paste a command you do not understand into a machine you care about. On a security team, a command you did not understand is how incidents start.
Keep a research log. Write down what you tried, what happened, and the link or source that helped. This turns a frustrating hour into reusable notes, feeds straight into your report's methodology, and means you never solve the same problem twice.
Judge your sources. Prefer official docs, then well-known community sites, then dated forum posts — in that order. Check the date on anything you find; a fix from years ago may not apply to your version. When two sources disagree, the official documentation wins.
Know when to ask for help. Research first is the rule, but stuck for a long time on the same wall is not a badge of honour. When you do ask, show what you already tried and what the exact error was — a good question is itself a research skill, and it gets you a far better answer.
The mindset: every professional in this field spends part of every day looking something up. The goal of this program is not for you to already know the answers — it is for you to get comfortable finding them. Treat each "I don't know how" as the actual work, not a detour from it.

Lab Architecture — Go Beyond the Minimum
The steps below are a working baseline, not the only correct way to build this lab. You are encouraged to research alternatives on your own — a different hypervisor, a different Linux distribution for the attacker box, a different network layout, or a different order of installation — and to document what you changed and why. Treat the official documentation for VirtualBox/VMware, Metasploitable2, DVWA, and Wazuh as your primary source, not this handbook. Two things stay fixed regardless of how you architect it: everything must run inside your own personally-owned lab, and your final network diagram must accurately reflect whatever you actually built.
At a minimum, your environment is built from three machines:
Machine 1 — Attacker. Flexible — WSL2, a dedicated attacker VM, or a second physical laptop all satisfy this role.
Machine 2 — Target. A Metasploitable2 virtual machine hosting DVWA and multiple intentionally vulnerable network services — the systems you assess in Week 2.
Machine 3 — Wazuh Server. A separate manager/dashboard install that receives logs from an agent on Machine 2 and turns your Week 2 attacks into Week 3 alerts.

Machine 1 — Attacker (Flexible)
This machine is not a fixed requirement — it is a role. Any of the following satisfy it, and you can research others:
WSL2. The default option. Install a Linux distribution, then install nmap, hydra, and a browser inside it.
A dedicated attacker VM. A lightweight Linux VM (e.g. Kali or plain Ubuntu with tools added) on the same bridged network as Machine 2. Use this if WSL2 cannot reach your target.
A separate physical laptop. If you have a second machine on the same home network, it can act as the attacker box directly — no virtualization required. Confirm it can reach Machine 2's IP before you rely on it.
Note: whichever option you pick, state it explicitly in your report's Methodology section and in your network diagram, so a reader knows exactly what generated your evidence.
Machine 2 — Target: Metasploitable2 + DVWA
Metasploitable2 is an intentionally vulnerable Ubuntu-based virtual machine that contains multiple intentionally vulnerable network services and web applications. It is your target server. DVWA (Damn Vulnerable Web Application) is one of the vulnerable web applications that runs on it — not a separate machine, but an application hosted inside the target. Keep this distinction in mind throughout the project: you attack the server's network services (like SSH) and you attack the web application (DVWA) that the server hosts.
Step 1 — Import Metasploitable2. Download the Metasploitable2 image from an official Rapid7 source, unzip it, and import it into VirtualBox or VMware as a new VM. Set its network adapter to Bridged, exactly like your other target VM options. Boot it and log in at the console with the well-documented default credentials, then immediately research how to change them — do not leave the default password in place for the rest of the engagement.
Step 2 — Confirm and enable services. From the Metasploitable2 console, check which services are already running (SSH, a web server, and a database are the ones you'll rely on). Research the command to list listening ports and running services on Linux, and use it to build the "what's running" note that Task 2.1 asks for — don't just copy a services list from the internet.
Step 3 — Install DVWA alongside it. Metasploitable2 already ships an Apache/PHP/MySQL stack, so DVWA can run on the same box as an additional site, or you can install DVWA on a second Ubuntu Server VM if you'd rather keep the two apart — either is an acceptable architecture as long as you document which one you chose. Either way you will need to: download DVWA's source, place it where the web server serves it from, create a dedicated MySQL database and user for it, and edit its config file to point at that database.
Step 4 — Set file permissions. DVWA needs its upload directory and its configuration file to be writable by the web server user, and nothing more permissive than that. Research the ownership and permission bits the web server process runs as, apply the minimum permissions that let DVWA function, and be ready to explain in your report why over-permissive settings (e.g. world-writable directories) would themselves be a finding.
Step 5 — Open the required ports. If a firewall is enabled on the target, allow inbound traffic on the required service ports — HTTP (80), FTP (21), and SSH (22) — so Machine 1 can reach the services required for Week 2, and, once installed, the Wazuh agent's outbound connection to Machine 3 — see the Ports & Services Reference table below for the full list. Research your distribution's firewall tool (e.g. ufw on Ubuntu) rather than disabling the firewall outright — opening only what you need is itself a demonstrable security control.
Step 6 — Verify from Machine 1. From your attacker machine, confirm DVWA's login page loads at Machine 2's IP address and that SSH is reachable, before you go any further.
Machine 3 — Wazuh Server
Step 1 — Provision the server. Create a third Ubuntu VM. If your hardware cannot comfortably run a separate Wazuh VM, use the Low-Resource Lab architecture described in Appendix F and connect your target agent to an instructor-provided or shared Wazuh server — do not combine the Wazuh server with the vulnerable target for the Core project; a real SOC would never co-locate its SIEM with a monitored host. Give it a bridged network adapter like the others.
Step 2 — Install the Wazuh manager, indexer, and dashboard. Use Wazuh's official single-node quickstart installer for this — it installs all three components together and is intended for exactly this kind of lab-scale deployment. Follow the current instructions on Wazuh's own documentation site, since installer commands change between versions; do not copy commands from an outdated blog post. Once it finishes, note the auto-generated admin credentials it prints out.
Step 3 — Open the dashboard. The dashboard listens on HTTPS. Confirm you can reach it from a browser using Machine 3's IP address and log in with the credentials from Step 2. Expect a self-signed certificate warning in your browser — that is normal for a lab deployment, not a finding against your own setup.
Step 4 — Install and enroll the agent on Machine 2. On the target VM, install the Wazuh agent package and configure it with Machine 3's IP address as its manager. Enrollment typically requires a registration step against the manager — follow Wazuh's current agent-enrollment documentation for your Linux distribution. Configure the agent to forward both the Linux authentication log and your web server/DVWA access log, since Week 3 depends on both being ingested.
Step 5 — Confirm the agent is Active. In the dashboard's Agents view, Machine 2 should show as Active with a recent check-in time. If it shows Disconnected or Never connected, research the agent's connection log on Machine 2 before assuming the manager is at fault — a mismatched manager IP or a blocked outbound port are the two most common causes.
Step 6 — Trigger and confirm your first security event. Before Week 2 begins, perform a small number of failed SSH login attempts against Machine 2 from Machine 1. Check the Wazuh dashboard to determine whether the activity generates an alert or appears as a collected authentication event instead. This verifies that the logging pipeline works before the full Week 2 exercises begin — confirming it now, on a small scale, saves you from discovering a broken pipeline three weeks from now.

Before You Move On — Verify Each Machine
If something later "doesn't work," it is almost always one of the checks below that was skipped. Do not start Week 2 until every one passes. The commands named here are starting points — research the exact syntax for your distribution.
Is the service actually running? On the target, confirm the web server, SSH, and database services are started (e.g. with a service-status command such as systemctl status). A stopped service is the most common cause of "connection refused."
Is the port listening? On the target, list the ports the machine is listening on (e.g. with ss or netstat) and confirm 80 and 22 appear. If a port is not listening, the service is not running or is bound only to localhost.
Is the firewall allowing it? Check the target's firewall status (e.g. ufw status). A service can be running and listening but still unreachable because the firewall is dropping the traffic. Allow only the ports you need — do not disable the firewall.
Can Machine 1 reach it? From the attacker machine, ping the target, then confirm the specific ports are open from the outside (a quick Nmap scan of the target does both jobs at once and doubles as your Task 2.1 evidence).
Does DVWA load and is it set up? Open DVWA in a browser from Machine 1, run its "Setup / Reset Database" step once, and set the security level to "low." A blank page or database error here usually means the DVWA config file points at the wrong database name, user, or password.
Is the Wazuh agent connected? In the Wazuh dashboard's Agents view, the target must show as Active, not Disconnected or Never connected. If it is not Active, the two usual causes are a wrong manager IP in the agent config or ports 1514/1515 being blocked between Machine 2 and Machine 3.
Hint: Work through these in order — running, listening, firewall, reachable. Each check assumes the one before it passed, so fixing them top-to-bottom is faster than guessing.
Understanding the Target — Its Attack Surface
The target is not just a website. It is a server with multiple attack surfaces. A common beginner mistake is to think of the target as "the DVWA site." In reality, the target is a whole server, and DVWA is only one of the things running on it. The server exposes network services (each on a port), and one of those services — the web server — hosts the DVWA application. Both the network services and the web application are things you can attack. Understanding this layout is the point of Week 2's reconnaissance.
The target's attack surface has two layers:
Network services. Programs the server runs that listen on a port and accept connections over the network — for example SSH (remote login), the web server (HTTP), a file transfer service (FTP), and a database. Each open port is a doorway into a service, and each service is a potential way in.
Web application. Sitting on top of the web service is DVWA, which has its own weaknesses — Brute Force, SQL Injection, XSS, and Command Injection. These are attacks against the application's logic and inputs, not against the network service itself.
Pictured as a tree, the target looks like this:
Metasploitable2 (Target Server)
├─ Network Services
│    ├─ SSH → SSH brute force (Task 2.8)
│    ├─ FTP → FTP user-login brute force (Task 2.7)
│    └─ Other exposed services
└─ Web Service (via HTTP)
     └─ DVWA
          └─ Brute Force, SQL Injection, XSS, Command Injection
This is the logic of the whole project: ports lead to services, services lead to attacks, one service hosts the application, the application has its own attacks, and every attack leaves evidence in a log that Wazuh can collect.
Notice the project deliberately includes two service-level authentication attacks (SSH and FTP) and one application-level authentication attack (DVWA Brute Force). As you work through Week 2 and Week 3, compare how the evidence each one generates differs — same underlying technique (credential guessing), three different layers, three different footprints in the logs.
The purpose is not to perform the same attack three times; it is to compare how the same credential-guessing technique produces different telemetry depending on the service or application being attacked.

Week 2 — Red Team Assessment (Network & Web Attack Surface)
Stage: Assessment
This phase introduces the mindset professionals call the Red Team: thinking like an attacker in order to find weaknesses before a real one does. Your objective is not advanced penetration testing — it is to carry out the required, well-understood attack simulations against your target and document them precisely enough for Week 3. Four of the required activities (Tasks 2.3–2.6) are application attacks against DVWA; the other two (Tasks 2.7–2.8) are network-service authentication attacks against FTP and SSH. Comparing how these different layers generate evidence is a deliberate part of the design — not a repeat of the same lesson.
Everything you do this week must stay inside the Rules of Engagement defined earlier: your own lab, nothing external. Run each attack from WSL (or your fallback attacker VM) against the target VM over the network — not locally on the target itself.
The Assessment Method: Recon Before Exploitation
Real attackers do not start by attacking. They work through stages, each answering a different question. Follow the same order this week — it keeps your evidence organized and your report credible.
Reconnaissance — "What can I see?" Discover the target's IP and which ports respond.
Enumeration — "What services are running?" Identify the service and, where possible, its version behind each open port.
Assessment — "What appears vulnerable?" Decide which services or application inputs look weak.
Exploitation / Attack Simulation — "Can I demonstrate the weakness?" Carry out the controlled attack.
Evidence — "Can I prove it?" Capture the screenshot, output, and timestamp before moving on.
Note that reconnaissance and enumeration (Nmap, service discovery) are not attacks — they are how you decide what to attack. This is why Task 2.1 comes first.
What You Should NOT Do
You are not being assessed on how much damage you can cause. You are being assessed on whether you can work through the full professional cycle:
identify → demonstrate → document → detect → investigate → explain → remediate
A clean, well-documented attack that you can detect and explain is worth far more than a dramatic one you cannot. Keep each attack controlled and small — just enough to prove the weakness exists and to generate the evidence you will need in Week 3.
Before You Attack — Capture a Baseline
Before you run a single attack, record what the environment looks like when nothing is wrong. Defenders call this a baseline — the "normal" you compare against later. Without it, you cannot tell what your attacks actually changed, and your Week 3 investigation loses its most useful reference point.
Capture and save, clearly labelled as "baseline":
The target's IP address, open ports, and running services.
The DVWA application loading normally in the browser.
The target's FTP and SSH services are reachable from the attacker environment.
The Wazuh agent showing as Active and the dashboard in its quiet, pre-attack state.
Required: take a baseline screenshot of the Wazuh dashboard before conducting the Week 2 attacks. In Week 3 you will compare it against the post-attack state to see exactly what your activity produced.

Week 3 — Investigation & Detection
Stage: Detection & Investigation
This week, SecureCorp's monitoring team has detected unusual activity on the customer portal. That activity is the required assessment activities (Tasks 2.3–2.8) you carried out in Week 2. Your task is now to switch sides: put on the Blue Team hat and investigate those same activities inside the Wazuh dashboard, as if you had no prior knowledge of what caused them.
This is the same technique real defenders use: correlating SIEM data against known attack patterns to determine what happened, when, and how serious it is.
You Are Now Changing Roles
During Week 2 you knew exactly what was happening, because you were the attacker. During Week 3, pretend you do not know what caused the activity. You are now a SOC analyst who arrives after the fact, sees only the evidence the security team collected, and must reconstruct the story. The discipline of setting aside what you already know — and letting the evidence speak — is the core skill of this week.
Week 2: "I did this attack."   →   Week 3: "I am a SOC analyst. What happened?"
Event → Alert → Investigation → Incident
Important: an event is not necessarily an alert. Some of your attacks will generate an automatic Wazuh alert. Others will only sit quietly in the collected logs and require you, the analyst, to go looking for them. Learning the difference is one of the strongest Blue Team lessons in this project. These four terms describe how raw activity becomes a declared incident:
Event — any single logged activity, such as one login attempt or one HTTP request. Most events are harmless.
Alert — an event, or pattern of events, that a rule flagged as worth a human's attention (for example, many failed logins in a row).
Investigation — the analyst's work of examining the alert and surrounding logs to decide what really happened.
Incident — a confirmed security event that has real impact and requires a response, such as confirmed unauthorized access.
Rough guide: a single failed login is an event; repeated failed logins is an alert; confirmed unauthorized access is an incident. Part of your job this week is to decide, for each activity, where it sits on that scale.

Appendix F — Alternative Lab Architectures
The main handbook assumes the default architecture below. If your hardware or network cannot support it, use one of these approved alternatives instead — note which one you used in your report's Methodology section.
Option A — Recommended (Default)
WSL2 (attacker) + Metasploitable2 target VM + Wazuh server VM, all on a Bridged network adapter. This is the architecture assumed throughout the handbook.
Option B — Dedicated Attacker VM
Use a lightweight Linux VM (e.g. Kali, or plain Ubuntu with Nmap/Hydra/Wireshark added) instead of WSL2 as your attacker environment. Choose this if WSL2 cannot reach your target VM even on a bridged network.
Option C — Low-Resource Lab
If your host cannot comfortably run three VMs at once, use an instructor-provided or shared Wazuh server if available, so your own machine only needs to run the attacker environment and the target VM. Confirm this option with your instructor before relying on it — it changes what you can independently demonstrate about Wazuh deployment in Task 1.5.
Option D — Advanced / Extended Lab
Dedicated attacker VM + target VM + Wazuh VM + the optional Windows VM with its own Wazuh agent, each on its own machine. This is the architecture to use if you are attempting the Stretch tier.
Whichever option you use, the Ports & Services Reference and "Before You Move On" verification checklist in the Lab Setup Guide still apply — the port numbers and troubleshooting order do not change with the architecture.
